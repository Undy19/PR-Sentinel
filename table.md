1. Бизнес-обоснование 
	

Зачем мы это делаем? Какая проблема решается? 
	

В современных dev-командах ревью PR - узкое место. Ревьюеры не успевают смотреть все пуллы, важные изменения с высоким риском теряются в потоке мелких PR-ов, а авторам приходится ждать обратную связь от суток до недели. Бот автоматизирует первичную фильтрацию: оценивает риск, находит пробелы в тестировании, рекомендует наиболее компетентного ревьюера на основе истории коммитов. Это сокращает time-to-review с часов до минут и снижает вероятность пропуска критических ошибок в production 

 

2. Цели проекта 
	

Что должно быть достигнуто? (SMART) 
	

    Разработать Telegram-бота, автоматически анализирующего каждый новый PR в GitHub/GitLab репозитории (измеримо: обработка 100% PR-ов без ручного триггера). 

    Генерировать 3-строчную оценку риска (LOW/MED/HIGH/CRITICAL) для каждого PR с обоснованием в течение 60 секунд после события (измеримо: 95% оценок за <60с). 

    Построить expertise graph, позволяющий автоматически рекомендовать 1-2 релевантных ревьюеров с точностью ≥70% (измеримо: совпадение с ручным выбором на выборке из 30 PR-ов). 

    Развернуть MVP на реальном учебном репозитории и провести пилотное тестирование с командой из 4 разработчиков в течение 2 недель 

3. Результаты (Product) 
	

Что будет произведено? (Перечень артефактов) 
	

    Исходный код бота (Python, репозиторий на GitHub с README, LICENSE, CI/CD). 

    Docker-образ с настроенным окружением (бот + webhook server). 

    Интеграция с GitHub API (webhook events) и Telegram Bot API. 

    Интеграция с LLM OpenAI API  для анализа риска. 

    SQLite база expertise graph с парсером git history. 

    Тестовая документация (unit + integration тесты, покрытие ≥60%). 

    Инструкция по развёртыванию и настройке (deployment guide). 

    Отчёт о пилотном тестировании с метриками. 

4. Критерии приемки 
	

Как поймем, что все сделано хорошо? 
	

    Бот реагирует на событие pull_request (opened/synchronize) в течение ≤5 секунд. 

    Каждое уведомление содержит: заголовок PR, уровень риска с эмодзи, 1-2 причины риска, рекомендованных ревьюеров. 

    Expertise graph корректно строится на репозитории с ≥50 коммитами и ≥3 авторами. 

    LLM-анализ работает стабильно (rate limit handling, retry logic при ошибках). 

    Все критические пути покрыты тестами; тестовый прогон проходит без ошибок. 

    Пилотное тестирование: ≥70% участников отмечают, что бот “ ускоряет/улучшает процесс ревью ” 

 

5. Ограничения 
	

Время, деньги, технологии, законы 
	

Время: 4 недели до MVP, 6 недель до полной версии. Бюджет: учебный проект - только free-tier API. Технологии: Python 3.11+, aiogram 3.x, PyGithub, FastAPI, SQLite. Масштаб: 1 репозиторий, ≤10 разработчиков, ≤50 PR/день. Законы: обработка только публичных репозиториев в пилоте (GDPR/данные сотрудников не затрагиваются). 

 

6. Допущения 
	

Что мы считаем верным (но не проверяли)? 
	

    Команда согласна использовать Telegram как канал уведомлений (уже используется). 

    GitHub App можно создать на учебном аккаунте и получить webhook access. 

    Git history репозитория достаточно полон для построения expertise graph. 

    Ревьюеры не будут воспринимать автоматические рекомендации как «микроменеджмент».
